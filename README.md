## Quickstart

The example calls `client.chat.get_completion` (GET `/chat/completions/{completion_id}`) with example values for its required arguments.

```rust
use openai_api::{ClientConfig, ClientAuthConfig, OpenAI};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = ClientConfig {
        // Optional: replaces the default server and any server an operation declares.
        base_url: Some("https://api.openai.com/v1".to_string()),
        auth: Some(ClientAuthConfig { api_key_auth: Some(std::env::var("API_TOKEN")?), ..Default::default() }),
        ..Default::default()
    };
    let client = OpenAI::new(config);
    let result = client.chat.get_completion("completion-1".to_string(), None)?;
    println!("{result:#?}");
    Ok(())
}
```

## Client behavior

- Base URL: `https://api.openai.com/v1`.
- Transport: ureq.
- Timeout: 30,000 ms per attempt.
- Retries: up to 3 attempts for status codes `408`, `425`, `429`, `500`, `502`, `503`, `504`, with 500–8,000 ms backoff.
- Idempotency: enabled for `POST`, `PATCH` using `Idempotency-Key`.
- Error telemetry: off. This build has no reporting endpoint and sends no error reports.

High-level operation methods return the typed response body directly. The low-level request layer returns an `SdkResponse<T>` envelope containing data, status, headers, request ID, latency, and attempt count.

## Raw responses and resources

Every operation that returns a body has a `*_with_response` companion taking the same arguments. It returns the `SdkResponse<T>` envelope: the decoded `data` beside `status_code`, `headers`, `request_id`, `latency` and `attempt`.

An operation that returns a named object model, or a list of them, returns `SdkResource<Model>`. Its fields read through `Deref`; `to_value()` returns the body exactly as the API sent it, as a `serde_json::Value` with wire names and unknown fields kept; `to_json()` returns the same body as a JSON string; `into_inner()` returns the model alone. Serializing or comparing a resource sees only the model's fields.

## Errors and response metadata

All failure paths use a small, predictable hierarchy:

| Error | Meaning |
| --- | --- |
| `SdkValidationError` | A request argument failed an OpenAPI constraint before network I/O. |
| `SdkHttpError` | The server returned a non-2xx response. |
| `SdkApiError` | A 2xx response whose error envelope, when the API declares one, reports a failed call. It carries the envelope's error code. |
| `SdkResponseDecodeError` | A 2xx response body or stream event did not decode into its declared type. It keeps the raw body. |
| `SdkNetworkError` | DNS, connection, TLS, or socket failure. |
| `SdkTimeoutError` | The configured per-attempt timeout elapsed. |

HTTP errors expose `status_code`, the response body and headers, plus `request_id` when the server supplies one. Preserve the request ID in support logs; it is the fastest way to correlate a failed SDK call with server-side traces.

Branch on common statuses with `kind()`, which returns an `SdkHttpErrorKind`: `BadRequest` (400), `Unauthorized` (401), `PermissionDenied` (403), `NotFound` (404), `Conflict` (409), `UnprocessableEntity` (422), `RateLimit` (429), `InternalServer` (any 5xx), or `Other` for any other status.

When the API declares a model for an error response, the SDK decodes the body into it as `error.data`, an `SdkErrorBody` with one variant per model. It is empty when the status declares no model or the body does not fit one. The raw body stays on the error either way, and `error.decode_body::<ErrorModel>()` decodes it into any `ErrorModel` by hand.

## Pagination

81 operations expose generated pagination helpers. Each operation has a `_paginated` companion whose callback can return `false` to stop early.

Pagination follows the cursor, offset, page-number, or next-URL contract declared by the OpenAPI operation. It stops when the API signals completion and does not prefetch the entire collection.

## Streaming

15 operations stream Server-Sent Events as an iterator of `Result<T, SdkError>`. The runtime handles SSE framing, ignores keep-alive comments, and treats `[DONE]` as the terminal marker. Cancel or stop iteration when the consumer no longer needs events so the underlying connection can close promptly.

## Project layout and API discovery

- Operation implementations are grouped under `src/methods/`.
- 2371 component models are split by API domain under `src/models/<domain>.rs` or `src/models/<tag path>/models.rs`, re-exported through the compatibility `types` module.
- Component schemas can choose a nested model folder with `x-octri-sdk-tags: ["Billing/Invoices"]`; the first tag owns the model and `/` creates nesting.
- [`sdk-manifest.json`](sdk-manifest.json) is the language-neutral public API index: operations, request/response modes, model properties, enum values, and generation settings.
- Public barrel/module exports are the compatibility boundary. Import public model names from those exports; internal domain filenames may evolve without changing model names.

## Local mock-server tests

The generated SDK includes a schema-derived, zero-dependency mock server and a
network contract suite. Node.js 20+ is required. Contract probes use authored response
examples only; schema-synthesized routes remain available to the local server.

`./scripts/mock --port 4010` starts the server. `./scripts/test` runs the mock contract suite, then native SDK tests. A zero-authored-example contract run succeeds with an explicit zero-test
summary; mismatches in authored examples still fail.
